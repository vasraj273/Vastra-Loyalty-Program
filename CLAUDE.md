# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-tenant loyalty-program backend for the VastraApp ecosystem. Manufacturers generate QR codes (printed on product/box stickers) in the **Vastra** app; retailers scan them in **YourApp** to earn points and redeem gifts. One FastAPI service serves three surfaces:

- **REST API** (`app/`) — the source of truth for Vastra, YourApp, and the panel.
- **React admin panel** (`panel/`, built to `panel/dist`, served at `/panel`) — manufacturer + super-admin UI.
- **Plain-HTML webview pages** (`app/web/`, served at `/web/*`) — the temporary mobile UI loaded inside the Vastra/YourApp webviews (`/web` retailer home, `/web/scan`, `/web/shop`, `/web/claims`, `/web/generate`).

Demo logins after seeding: `admin/admin123` (super admin), `surya/surya123` & `heritage/heritage123` (manufacturers), retailer logins are `<shop-first-word>/<that>123` (e.g. `kumar/kumar123`).

## Database — the central design

`app/database.py` is **dual-backend**: PostgreSQL when `DATABASE_URL` is set (production / Neon), SQLite otherwise (local dev, no setup). Application code is written in **sqlite style everywhere** (`?` placeholders, `cur.lastrowid`, `db.executescript`, named `:param` dicts, `datetime('now')`/`date('now')`); a thin `_PGConn` adapter translates these to psycopg at runtime. Consequences when editing SQL:

- New code keeps using `?`, `cur.lastrowid`, `datetime('now')` — do not write Postgres-specific SQL in `app/main.py`.
- **Any table whose INSERT uses `cur.lastrowid` must be listed in `_ID_TABLES`** in `database.py`, or `lastrowid` is `None` on Postgres (the adapter appends `RETURNING id` only for those tables).
- Avoid `%` literals (e.g. `LIKE '%x%'`) and inline `:word` time formats — the adapter's `?`→`%s` and `:name`→`%(name)s` translation would break.
- **No `;` inside `SCHEMA` comments.** The PG adapter's `executescript` splits on `;`; a semicolon in a `--` comment would cut a statement in two (SQLite tolerates it, so it only breaks on Postgres at deploy). The adapter now strips full-line `--` comments before splitting, but keep comments semicolon-free.

**Never reseed or drop the production (Neon) database to apply schema changes.** Schema evolution is additive and idempotent: add new tables to `SCHEMA` (created via `CREATE TABLE IF NOT EXISTS`), and add new columns to the `_MIGRATIONS` list. `migrate()` runs on every startup and applies missing columns in place (`ADD COLUMN IF NOT EXISTS` on PG; PRAGMA-checked on SQLite). The app startup only does `init_db()` + `migrate()` + `create_constraints()` + `_backfill_coords()` + `_backfill_product_snapshots()`; it never seeds. `seed.py`/`reset_db()` are destructive and for local dev or one-time initial seeding only.

## Architecture essentials

**Two auth principals, token-based** (`app/auth.py`). Manufacturers/super-admin authenticate via `auth_tokens`; retailers via `retailer_tokens`. Dependencies: `current_manufacturer`, `current_admin` (super admin only, owns no catalog data), `current_retailer`. Tokens are opaque; sent as `Authorization: Bearer` or `?token=` (the latter lets the print-PDF link open in a tab). Passwords are PBKDF2 (`hash_password`/`verify_password`).

**SSO for native apps (token exchange).** `POST /auth/sso/manufacturer` and `POST /auth/sso/retailer` let native Vastra/YourApp builds skip a second login: the parent backend mints a short-lived **HS256 JWT** (verified by `verify_sso_assertion` in `app/auth.py`), and the exchange mints the **same opaque tokens** the existing `current_*` deps already validate — so no other endpoint changes. Config is env-only, mirroring `QR_BASE_URL`: `SSO_SECRET` (required to enable; unset → endpoints return `503`), `SSO_ISSUERS` (default `vastra,yourapp`), `SSO_AUDIENCE` (default `loyalty`), `SSO_MAX_AGE` (default `120`s, bounds replay via an `iat` freshness check). Principals are matched by **`external_id`** and must already be provisioned — the exchange **never auto-creates** (unknown/cross-tenant → `403`, bad/expired assertion → `401`). The verify helper pins `algorithms=["HS256"]` (rejects `alg:none`), checks `aud`/`iss`/`role`/`exp`/`iat`, and takes identity only from the signed `sub`. Retailer assertions carry `manufacturer_external_id` so a retailer is resolved strictly within its tenant. Manufacturer password login stays (the web panel has no parent session to exchange); retailer access is SSO-only in production.

**Retailer logins are auto-created.** `POST /retailers` (and `seed.py`/`backfill_retailer_logins.py`) derive a login from the shop name: username = first word, lowercased alphanumerics; password = `<username>123`; a clash gets the retailer id appended (the `username` column is `UNIQUE`). The creation response returns the plaintext password once so the panel can show the manufacturer the new credentials.

**Multi-tenancy.** Every product/retailer/distributor/scheme/batch/gift/claim/ledger row carries `manufacturer_id`; all manufacturer endpoints filter by `current_manufacturer["id"]`. A retailer belongs to one manufacturer; cross-manufacturer scans are rejected. Retailer-facing endpoints (`/scan`, `/retailer/*`) derive the retailer from the token — never from a request body — so points can only be credited to the logged-in retailer.

**Distributor layer (manuf → distributor → retailer).** `distributors` is a manufacturer-scoped entity for **tracking/attribution only** — no login, no wallet, no points. A retailer optionally links to one via `retailers.distributor_id`. Each scan denormalizes `points_ledger.distributor_id` at scan time (point-in-time, like `region`), so reassigning a retailer never rewrites history. `POST /retailers/import` bulk-creates retailers from CSV text (sent as JSON, no `python-multipart`): a `distributor` column find-or-creates the distributor by name (`_find_or_create_distributor`) and links it; an optional `external_id` column sets the SSO mapping id (unique per manufacturer, used by `/auth/sso/retailer`); retailer logins are auto-created via the shared `_assign_retailer_login`. The dashboard `by_distributor` rollup sums the *retailers'* scans/points grouped by distributor — never points held by the distributor itself.

**CSV import (all three catalogs).** All imports take CSV text as JSON (no `python-multipart`) and report `created`/`skipped`/`errors`: `POST /retailers/import` (above), `POST /distributors/import` (columns `name`/`phone`/`region`, skip existing names), and `POST /products/import` (columns `name`/`sku`/points — the points column is matched under several aliases like `PointsPerScan`/`points`/`loyalty_points` via `_row_points`; it **upserts** by SKU, *updating* a product you already own rather than skipping, and also reports `updated`). The panel surfaces these as an **Import CSV** button on the Customers, Distributors, and Products tabs (shared `panel/src/components/ImportResult.jsx`).

**The wallet ledger.** `points_ledger` is a typed transaction log (`entry_type`: `scan`, `gift_redeem`, `refund`, `adjustment`, `transfer`). A retailer's **balance = SUM(points)** across all entries; **scan analytics filter `entry_type='scan'`** (dashboard, claims, region/product aggregates). When adding a balance-changing feature, write a ledger row rather than mutating a balance field.

**Points are frozen at generation.** `qr_batches.points_per_code` is captured when codes are generated, so reprinting/old stickers keep their promised value even if the product's `loyalty_points` later change. Schemes add a time-bound bonus on top at scan time; the most generous active scheme covering the product wins (no stacking), and the base/bonus split + paying scheme are recorded on the ledger row.

**Products: Vastra is the System of Record (reference + snapshot).** Loyalty no longer joins the `products` table on the QR/scan/claims/analytics/wallet paths. `qr_batches` and `points_ledger` carry a product **reference** (`product_external_id`) + immutable **snapshot** (`product_name`/`product_sku`), and `qr_batches` carries its own `manufacturer_id` (batch tenancy no longer flows through the product). `POST /qr/generate` is **dual-contract**: the primary contract takes `product_external_id` + `product_name` + `product_sku` + `points_per_code` from the Vastra backend and does **no** products lookup; a legacy `{product_id}` body is still accepted (panel / `/web/generate`) and resolved once into the same snapshot. `_backfill_product_snapshots()` (startup, idempotent) fills the snapshot columns for pre-migration rows. **Transitional, kept for now:** the `products` table, product CRUD + `/products/import`, the Products panel tab, and `scheme_products` (still keyed by `product_id`, so product-specific scheme bonuses apply only to legacy `product_id` batches). When editing QR/scan/claims/analytics SQL, read the snapshot columns — do not re-introduce a `products` join. See `docs/integration/PRODUCT_INTEGRATION.md`.

**Parent/child QR (boxes).** `qr_codes` rows are children by default; if `items_per_box` is set at generation, parent (box) codes are created with children pointing at them via `parent_token`. Scanning a parent registers all still-unredeemed children at once and sums their points. A box scan therefore writes **one `points_ledger` row per child**; `GET /claims` re-collapses them for display by grouping on `COALESCE(q.parent_token, l.token)` (join `qr_codes`), returning `item_count` + `parent_token` so the panel shows a single `📦 Box · N items` row. This grouping is **query-time only** (no `scan_event_id` column) — keep it that way so it stays correct for data already on Neon. The box (parent) sticker in `app/pdf_service.py` keeps its title/name/code inside the border, so its QR is sized smaller than a child sticker's.

**QR payload.** Each code encodes `{QR_BASE_URL}/{token}` (default `/web/scan`); set `QR_BASE_URL` to the deployed HTTPS origin before any production print run, or printed codes point at the wrong host. The 6-char `manual_code` is the typed fallback for damaged stickers. The token is a `uuid4().hex` lookup key — opaque, unguessable, and validated server-side (unknown → 404), so tampering with the URL can't corrupt anything; `scan.html` cosmetically rewrites the address bar to `/web/scan` after reading it.

**Retailer location & the map.** Two layers, distinct on purpose: (1) the **retailer's shop pin + address** — `retailers.lat/lng`, `location_source` (`city` = resolved from the typed region via `geo.coords_for`; `gps` = captured from a scan), and `retailers.address` (a precise street address). These are **refreshed every scanning session — latest wins** (via `POST /retailer/location`): the pin moves, `region` is re-derived from `geo.nearest_city`, and the address is reverse-geocoded best-effort by `geo.reverse_address` (free OpenStreetMap Nominatim; falls back to the previous value / the city / the coordinates). So a wrong city entered at registration self-corrects to the real one. `region` is **optional** at registration. The Customers tab shows the address + a Google Maps **"View on map"** link to the exact pin. (2) **Per-scan location** — `points_ledger.lat/lng`, sent with `POST /scan`. The dashboard `map_points` plots scan *events* (bucketed ~11m, weighted by count), **clustered** via `leaflet.markercluster` with street-level zoom, falling back to the shop pin for scans with no location. **Location is asked up front**, before scanning, via a trust-framed popup in `scan.html` (high-accuracy GPS, secure-context required); if the retailer can't/won't grant it they close the popup (✕) and the scan falls back to their **registered city** — scanning is never hard-blocked.

**Panel ↔ API.** `panel/src/api.js` is the only fetch layer: dev hits the Vite proxy (`/api` → `:8000`), production is same-origin (`/panel` served by the API). Manufacturer session token lives in `localStorage` (`vl_token`); retailer webviews use `vl_rtoken`. Navigation is a single top-right **burger menu** (`App.jsx`) listing the tabs + Log out. Every points-changing action (adjust/transfer/approve/reject; gift claim in the webview) is gated by a themed confirmation dialog — in the panel via the promise-based `useConfirm()` (`panel/src/confirm.jsx`, mounted by `ConfirmProvider` in `main.jsx`). The panel renders manufacturer tabs (Dashboard, Customers, Distributors, Products, Schemes, Gifts, Claims, Redemptions) or, for super admin, the Manufacturers tab. Every data tab has an **Export CSV** button backed by a shared client-side helper `panel/src/utils/csv.js` (`downloadCSV(filename, columns, rows)` — RFC-4180 + BOM `Blob`, no dependency, no new endpoint); Claims walks all pages and Redemptions exports all three statuses. **Generate QR** on the Products tab opens an in-panel modal `panel/src/components/GenerateQrModal.jsx` (it calls the existing `/qr/*` endpoints via `api.js` + `printUrl`), so the standalone `/web/generate` page is no longer linked from the panel (it still works on its own). The retailer webviews (`home/scan/shop/claims`) share their own top-right burger menu (Home/Scan/Reward shop/Claims history/Log out), and `scan.html` plays a count-up + confetti animation on a successful scan (and reopens the camera on "Scan another").

**Theming.** The Vastra brand palette is a set of CSS variables in `panel/src/styles.css` `:root` (`--primary` `#0191d0`, `--indigo` `#1d466f` dark blue, `--madder` `#fb624b` coral, `--ink` `#112134`, light `--paper`/`--card`; `--leaf`/`--gold` kept as functional approved/pending status colors). The **same `:root` block is duplicated inline in every `app/web/*.html`** — change all of them together, plus the non-variable literals that derive from the palette (chart colors in `Dashboard.jsx`/`BarChart.jsx`, the `scan.html` confetti array, Leaflet `.scan-dot`/`.marker-cluster` colors, `.error`/badge tints, modal `.backdrop`/`.modal-backdrop` overlays). Font is a **Helvetica system stack** (no web-font link); headings are bold, codes/tokens use a monospace stack. **QR codes stay black/white** (`app/qr_service.py`) for scanner reliability — don't tint them.

**Dashboard analytics (`GET /analytics/dashboard`, manufacturer-scoped).** Returns `totals` (retailers, products, scans, points_awarded, codes_issued, **redeem_total/redeem_pending/redeem_approved** from `gift_claims`), `by_region`/`by_product`/`by_distributor`/`top_retailers`, `map_points` (clustered Leaflet India scan map via `leaflet.markercluster`), and **`by_month`** (`{month:'YYYY-MM', generated, scanned}` — generation from `qr_codes.created_at`, scans from `points_ledger.scanned_at`). The Dashboard shows two stat rows (funnel totals + redemption requests), the region/distributor tables, and a **QR analytics** section with a year selector + two themed SVG bar charts (`panel/src/components/BarChart.jsx`, no charting dependency). Month buckets use `substr(x, 1, 7)` — **not** `strftime` — to stay portable across SQLite and Postgres. Blank/NULL regions roll up under `'Unspecified'` (`COALESCE(NULLIF(region, ''), 'Unspecified')`). Cards are all-time; the charts are per-month within the selected year (each chart shows a per-year subtotal so the bars reconcile).

## Deployment

`Dockerfile` builds the panel then runs the API serving everything (`/`, `/panel`, `/web/*`). Render/Neon: set `DATABASE_URL` (Neon pooled string) and `QR_BASE_URL=https://HOST/web/scan`; set `SSO_SECRET` to enable native-app SSO (unset → SSO endpoints inert). The container creates/migrates tables on boot but never seeds — data persists across deploys. The `external_id` columns and their unique indexes are added idempotently by `migrate()`/`create_constraints()` like any other additive change. See `DEPLOY.md`.
