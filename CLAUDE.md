# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-tenant loyalty-program backend for the VastraApp ecosystem. Manufacturers generate QR codes (printed on product/box stickers) in the **Vastra** app; retailers scan them in **YourApp** to earn points and redeem gifts. One FastAPI service serves three surfaces:

- **REST API** (`app/`) — the source of truth for Vastra, YourApp, and the panel.
- **React admin panel** (`panel/`, built to `panel/dist`, served at `/panel`) — manufacturer + super-admin UI.
- **Plain-HTML webview pages** (`app/web/`, served at `/web/*`) — the temporary mobile UI loaded inside the Vastra/YourApp webviews (`/web` retailer home, `/web/scan`, `/web/shop`, `/web/claims`, `/web/generate`).

## Database — the central design

`app/database.py` is **dual-backend**: MySQL (8.0.13+) when `DATABASE_URL` is set (production / AWS RDS), SQLite otherwise (local dev, no setup). Application code is written in **sqlite style everywhere** (`?` placeholders, `cur.lastrowid`, `db.executescript`, named `:param` dicts, `datetime('now')`/`date('now')`); a thin `_MyConn` adapter translates these to PyMySQL at runtime. Provisioning requirements for the database owner live in `docs/integration/MYSQL_SETUP.md`. Consequences when editing SQL:

- New code keeps using `?`, `cur.lastrowid`, `datetime('now')` — do not write MySQL-specific SQL in `app/main.py`. (`cur.lastrowid` needs no registration: MySQL supports it natively.)
- **Never `%` literals** (e.g. `LIKE '%x%'`) or inline `:word` time formats — the adapter's `?`→`%s` and `:name`→`%(name)s` translation would break, and PyMySQL's bulk-insert path also `%`-formats the INSERT prefix. This is why `_translate` emits `CAST(UTC_TIMESTAMP() AS CHAR)` rather than `DATE_FORMAT(...)`.
- **Any indexed/UNIQUE/PK text column must be `VARCHAR(n)`, never `TEXT`** — MySQL cannot index a bare TEXT. `SCHEMA` is written so one declaration serves both backends (SQLite takes affinity from the type name and ignores the length): `VARCHAR(n)`/`MEDIUMTEXT` → TEXT, `DOUBLE` → REAL. Same rule applies to `_MIGRATIONS` declarations.
- **No `;` inside `SCHEMA` comments.** The adapter's `executescript` splits on `;`; a semicolon in a `--` comment would cut a statement in two (SQLite tolerates it, so it only breaks on MySQL at deploy). The adapter strips full-line `--` comments before splitting, but keep comments semicolon-free.
- **A literal default on a TEXT column must be written `DEFAULT ('')`**, not `DEFAULT ''` — MySQL only accepts the expression form. SQLite accepts both.
- **MySQL has no partial indexes and no `IF [NOT] EXISTS` for indexes/columns.** `_INDEXES`, `_MYSQL_CONSTRAINTS` and `migrate()` guard every statement with an `information_schema` lookup instead. The `entry_type`-scoped unique index is rebuilt as the **stored generated column** `points_ledger.active_scan_token` — never write to it; it recomputes to NULL when a scan is reversed, which is what frees the token for a rescan.
- **MySQL silently ignores inline `REFERENCES`** written inside a column definition — it parses them and creates nothing. `_mysql_foreign_keys()` parses `SCHEMA` and re-emits them as table-level `ADD CONSTRAINT`, so a new `REFERENCES` clause needs no separate bookkeeping.
- **`get_db()` pins `READ COMMITTED` and `time_zone = '+00:00'` per connection.** Both are load-bearing, not hygiene. Under InnoDB's default REPEATABLE READ the gift-claim guard's `SELECT ... FOR UPDATE` still re-reads a stale snapshot — measured: 12 of 20 concurrent claims succeeded and the wallet hit −1090. Timestamps are stored and compared as UTC strings, so a local-time server would corrupt the dashboard's month buckets.

**Never reseed or drop the production database to apply schema changes.** Schema evolution is additive and idempotent: add new tables to `SCHEMA` (created via `CREATE TABLE IF NOT EXISTS`), and add new columns to the `_MIGRATIONS` list. `migrate()` runs on every startup and applies missing columns in place (information_schema-checked on MySQL; PRAGMA-checked on SQLite). The app startup only does `init_db()` + `migrate()` + `create_constraints()` + `_backfill_coords()` + `_backfill_product_snapshots()`; it never seeds. `seed.py`/`reset_db()` are destructive and for local dev or one-time initial seeding only (`ALLOW_MYSQL=1` is required against MySQL).

**Collation is split on purpose.** Credentials and identifiers are case-**sensitive**: `manufacturers.username`, `retailers.username`, `qr_codes.token`/`parent_token`/`manual_code`, `points_ledger.token`, both token tables, `gift_claims.reference` and both `external_id`s carry `COLLATE utf8mb4_bin`, so they compare byte-for-byte exactly as on SQLite. Descriptive text (shop names, people's names, regions, notes) keeps the case-**insensitive** database default (`utf8mb4_0900_ai_ci`) so search and analytics grouping behave naturally. Passwords need no collation: `verify_password` runs PBKDF2 in Python and `password_hash` is never compared in SQL. A foreign key's collation must match its referent — that's why `points_ledger.token` is binary too. The `{CS}` placeholder in `_SCHEMA_TMPL`/`_MIGRATIONS` expands to the collation on MySQL and to nothing on SQLite.

**Testing both backends.** `pytest tests/ -q` runs the whole suite on throwaway SQLite. Setting `DATABASE_URL` runs the *same* suite against MySQL and additionally un-skips two MySQL-only proofs: `test_race_mysql.py` (20-thread scan/claim concurrency against a live uvicorn) and `test_mysql_schema.py` (DDL idempotency across two startups, all 24 foreign keys, cascade behaviour, the generated-column index including release-on-reversal, the collation split, and UTC timestamp format).

## Architecture essentials

**Two auth principals, token-based** (`app/auth.py`). Manufacturers/super-admin authenticate via `auth_tokens`; retailers via `retailer_tokens`. Dependencies: `current_manufacturer`, `current_admin` (super admin only, owns no catalog data), `current_retailer`. Tokens are opaque; sent as `Authorization: Bearer` or `?token=` (the latter lets the print-PDF link open in a tab). Passwords are PBKDF2 (`hash_password`/`verify_password`). **Logins are compared exactly** — both login endpoints match `username` byte-for-byte (only surrounding whitespace is trimmed); stored usernames are canonicalised to lowercase at creation (`create_manufacturer`, `_assign_retailer_login`, `_vastra_username`), so a login is typed in lowercase. **Single active session:** `issue_token`/`issue_retailer_token` delete the principal's existing tokens before inserting the new one, so at most one token row survives per user (a new login on any device/path — password *or* SSO — invalidates the old one). Logout still deletes the token; there is no expiry column. **Emergency lockout:** `manufacturers.blocked`/`retailers.blocked` (`INTEGER DEFAULT 0`, flipped by hand in the DB) — when `1`, login is refused (`403 Account is blocked`) and `current_user`/`current_retailer` reject the account's existing token on its next request (= automatic logout). Set back to `0` to restore.

**SSO for native apps (token exchange).** `POST /auth/sso/manufacturer` and `POST /auth/sso/retailer` let native Vastra/YourApp builds skip a second login: the parent backend mints a short-lived **HS256 JWT** (verified by `verify_sso_assertion` in `app/auth.py`), and the exchange mints the **same opaque tokens** the existing `current_*` deps already validate — so no other endpoint changes. Config is env-only, mirroring `QR_BASE_URL`: `SSO_SECRET` (required to enable; unset → endpoints return `503`), `SSO_ISSUERS` (default `vastra,yourapp`), `SSO_AUDIENCE` (default `loyalty`), `SSO_MAX_AGE` (default `120`s, bounds replay via an `iat` freshness check). Principals are matched by **`external_id`** and must already be provisioned — the exchange **never auto-creates** (unknown/cross-tenant → `403`, bad/expired assertion → `401`). The verify helper pins `algorithms=["HS256"]` (rejects `alg:none`), checks `aud`/`iss`/`role`/`exp`/`iat`, and takes identity only from the signed `sub`. Retailer assertions carry `manufacturer_external_id` so a retailer is resolved strictly within its tenant. Manufacturer password login stays (the web panel has no parent session to exchange); retailer access is SSO-only in production.

**YourApp server-to-server scan (phone-verified).** YourApp's backend calls `POST /yourapp/qr/lookup` (read-only code preview: product snapshot, base/bonus/total points via `_best_scheme`, `status: available|redeemed`, box item count, redeeming shop) and `POST /yourapp/scan` (body `phone` + `code` + optional separate `lat`/`lng`) — no retailer session or SSO exchange. Auth is a shared secret in the `X-API-Key` header checked by `require_yourapp_key` (`hmac.compare_digest`); config is env-only like `SSO_SECRET`: `YOURAPP_API_KEY` unset → both endpoints `503`. The retailer is resolved by **phone number** via `_retailer_by_phone`: normalization = digits only, last 10 kept (`_norm_phone`, tolerates `+91`/spaces/dashes), matched in Python against the retailers of the **scanned code's manufacturer** (`qr_batches.manufacturer_id`), so tenancy comes from the code and a phone can never credit cross-tenant. No match → `403`, several matches → `409` (data cleanup signal), `blocked` → `403`; unknown code keeps the enumeration-proof `404 "Invalid code"`. The redemption core is shared: `/scan` and `/yourapp/scan` both call `_redeem_code` (with `_find_code`), so box logic, scheme bonus, conditional-UPDATE race safety, and the response shape are identical. `/yourapp/scan` with lat/lng also runs the same latest-wins shop-pin refresh as `POST /retailer/location` (shared `_refresh_retailer_pin`, best-effort — a geocode failure never fails the scan). Because phone is an identity key, `POST /retailers/import` rejects rows whose normalized phone duplicates another retailer of the same manufacturer (missing phone stays allowed — webview-only retailers). Rate limit: `RL_SCAN`, keyed by IP for these endpoints (one YourApp server = one bucket; raise `RL_SCAN` if bulk volume needs it).

**Manufacturer OTP login via Vastra (panel).** The panel's Login screen is dual-mode: password, or **Vastra mobile + OTP** (`POST /auth/vastra/send-otp` → `POST /auth/vastra/verify-otp`, both rate-limited like login). Verify calls Vastra's `loyalty-signup`/`loyalty-verifyotp` APIs via `app/vastra_client.py` (the **only** module that talks to Vastra; env-configured: `VASTRA_API_BASE_URL` — unset → feature fails closed, `VASTRA_API_KEY`, `VASTRA_API_TIMEOUT` default `10`s, `VASTRA_UDID`/`VASTRA_DEVICE_TYPE` fixed device headers). On success the manufacturer is matched by `external_id` (= Vastra `organization_Id`) or **auto-provisioned** (unlike SSO) with a random throwaway password, `display_name` is refreshed from the org name, and Vastra's **`access_token` is stored server-side** in `manufacturers.vastra_access_token` — nothing reads it today (the catalog is CSV-imported; see Products below), it is kept for a future catalog reconnect. `/auth/logout` wipes the stored Vastra token along with the session token. Vastra errors map: rejection → `401`/`403` with Vastra's own message, transport/config failure → `502`.

**Retailer logins are auto-created.** `POST /retailers` (and `seed.py`/`backfill_retailer_logins.py`) derive a login from the shop name: username = first word, lowercased alphanumerics; password = `<username>123`; a clash gets the retailer id appended (the `username` column is `UNIQUE`). The creation response returns the plaintext password once so the panel can show the manufacturer the new credentials.

**Multi-tenancy.** Every product/retailer/distributor/scheme/batch/gift/claim/ledger row carries `manufacturer_id`; all manufacturer endpoints filter by `current_manufacturer["id"]`. A retailer belongs to one manufacturer; cross-manufacturer scans are rejected. Retailer-facing endpoints (`/scan`, `/retailer/*`) derive the retailer from the token — never from a request body — so points can only be credited to the logged-in retailer.

**Distributor layer (manuf → distributor → retailer).** `distributors` is a manufacturer-scoped entity for **tracking/attribution only** — no login, no wallet, no points. A retailer optionally links to one via `retailers.distributor_id`. Each scan denormalizes `points_ledger.distributor_id` at scan time (point-in-time, like `region`), so reassigning a retailer never rewrites history. `POST /retailers/import` bulk-creates retailers from CSV text (sent as JSON, no `python-multipart`): a `distributor` column find-or-creates the distributor by name (`_find_or_create_distributor`) and links it; an optional `external_id` column sets the SSO mapping id (unique per manufacturer, used by `/auth/sso/retailer`); retailer logins are auto-created via the shared `_assign_retailer_login`. The dashboard `by_distributor` rollup sums the *retailers'* scans/points grouped by distributor — never points held by the distributor itself.

**CSV import (retailers, distributors, products, gifts).** Imports take CSV text as JSON (no `python-multipart`) and report `created`/`skipped`/`errors`: `POST /retailers/import`, `POST /distributors/import`, `POST /catalog/products/import` (also `updated`, and takes a `mode`) and `POST /gifts/import`. The panel surfaces each as an **Import CSV** button on the Customers, Distributors, Products and Gifts tabs (shared `panel/src/components/ImportResult.jsx`, whose `ColumnMap` export renders the resolved mapping).

**Headers are matched, never dictated.** Every import resolves its fields with `_pick_col(fields, norm, aliases)` against alias tuples, normalised by the shared `_norm_header` — so each list imports exactly as it falls out of the manufacturer's own system, with no hand-edited header row. **Alias order beats column order** (that is the whole point of `_pick_col` over a plain `next()`): a retailer file carrying both `Shop Name` and `Name` resolves each to the right field regardless of which column comes first. Shared tuples: `_CSV_PHONE_HEADERS` (`Mobile`, `Contact No`, `WhatsApp`…), `_CSV_REGION_HEADERS` (**`city` before `state`** — the client's export has both and the city is the better pin for `geo.coords_for`). Per-entity: `_CSV_NAME_HEADERS`/`_CSV_CODE_HEADERS`/`_CSV_POINTS_HEADERS` (products — points includes **`retailer_points`**, the client's spelling; their `distributor_points` is deliberately *not* matched), `_CSV_DIST_NAME_HEADERS`, `_CSV_RET_*` (shop/name/address/distributor/external_id), `_CSV_GIFT_*` (name/points/description/image). Only the identity columns are required — retailers need a shop *or* name column, gifts need a name *and* a points column, products need name *and* code, distributors need a name; everything else is optional and unmatched columns are ignored (products alone keep them, in `attrs`). **For retailers the shop-or-name rule is per row, not just per file:** a file carrying both `Firm Name` and `Name` fills the firm in only for shops that trade under one, so a blank shop cell falls back to the person's name and the row still imports (rejecting those cost a real 2230-row import 420 rows). Only a row with *neither* is an error. Two rules worth knowing: `_CSV_RET_EXTERNAL_ID_HEADERS` is deliberately narrow (`external_id` only) because it is the SSO identity key and must never be guessed from an `id` column; and `_first_image` unwraps the JSON-array image cell (`["https://…"]`) the gift export writes into the single `gifts.image_url`, dropping their `"undefined"` placeholder. Every import echoes a `columns` map of `{field: matched header}` so the panel can show what was actually read — a dropped column is otherwise invisible.

**Retailer import dedupes on phone.** `POST /retailers/import` skips a row whose normalized phone already belongs to a retailer of this manufacturer, and only falls back to shop-name matching when the row has no phone (webview-only retailers). Phone is the right key because it is what `/yourapp/scan` resolves a retailer by, and because real customer lists legitimately repeat an owner's first name across different shops — name-based dedupe silently dropped those. A `distributor` column is still find-or-created and linked (matched case-insensitively against the existing distributors first, so a customer list imported after the distributor list attaches to those rows instead of creating near-duplicates), logins are still auto-created, and the response still returns the plaintext credentials once.

**The customer list carries its wallet balances over.** Real customer exports ship the retailer's *current* points ("Point Balance" in the client's file; `_CSV_RET_POINTS_HEADERS`, balance spellings ahead of a bare `points` so a file with several points columns credits the right one). Each new retailer's balance is written as **one `points_ledger` row of `entry_type='import_opening'`** — the wallet and the Customers tab's Points column pick it up (balance = SUM over all entries), while every `entry_type='scan'` filter ignores it, because a carried-over number is not scan history and must not inflate the dashboard funnel or the region/product analytics. Only *newly created* retailers are credited: a row skipped as a duplicate is left entirely alone, so re-importing a stale list can neither double-credit nor claw back points earned since. Negative cells are refused (the wallet has no debt) and reported in `errors`; `'14.00'`, `'1,005.00'` and `'₹ 500'` all parse (`_parse_points`).

**"Delete all" (bulk clear).** Each imported list has a collection-level DELETE behind a themed confirm, so a bad import can be undone without deleting rows one at a time: `DELETE /catalog/products` (imported catalog rows only), `DELETE /distributors`, `DELETE /retailers` and `DELETE /gifts`. All are manufacturer-scoped. **Each one enforces exactly the rule its single-row delete enforces, but skips instead of 409-ing** — a bulk clear must not be blocked by one protected row: retailers with `points_ledger` history are kept (their points and claims need an owner) — **except an `import_opening` row, which does not protect its retailer and is deleted with it**, since a balance carried over by the very import being undone is part of that import, not history (both `DELETE /retailers/{id}` and `DELETE /retailers` apply this rule) — gifts with `gift_claims` are kept (a claim must keep pointing at what was redeemed), and distributors are always deletable because their retailers are merely unlinked and `points_ledger.distributor_id` is denormalized history with no FK. Retailers/gifts return `{deleted, skipped}` so the panel can explain the survivors; distributors and products return `{deleted}`.

**The wallet ledger.** `points_ledger` is a typed transaction log (`entry_type`: `scan`, `gift_redeem`, `refund`, `adjustment`, `transfer`, `scan_reversed`, `reversal`, `import_opening`). A retailer's **balance = SUM(points)** across all entries; **scan analytics filter `entry_type='scan'`** (dashboard, claims, region/product aggregates). When adding a balance-changing feature, write a ledger row rather than mutating a balance field. **Scan reversal** (`GET /scans/lookup` + `POST /scans/reverse`, manufacturer-scoped; Claims tab lookup box + row action): when the wrong retailer scanned a code, the original scan rows flip to `scan_reversed` (so every `entry_type='scan'` filter excludes them with no query changes), an offsetting negative `reversal` row per item deducts the exact credited points (409 if the wallet can't cover it — no negative balances), and the code(s) get `redeemed_at`/`redeemed_by` cleared so the rightful retailer can rescan (box scans reverse whole). The scan-token unique index is scoped to `entry_type='scan'` (`uq_ledger_active_scan_token`; the old `uq_ledger_scan_token` is dropped idempotently in `_CONSTRAINTS`) so the reversed row, the reversal row, and the rescan row can share a token.

**Points are frozen at generation.** `qr_batches.points_per_code` is captured when codes are generated, so reprinting/old stickers keep their promised value even if the product's `loyalty_points` later change. Schemes add a time-bound bonus on top at scan time; the most generous active scheme covering the product wins (no stacking), and the base/bonus split + paying scheme are recorded on the ledger row.

**Products: the catalog is the manufacturer's own CSV import (reference + snapshot).** Loyalty no longer joins the `products` table on the QR/scan/claims/analytics/wallet paths. `qr_batches` and `points_ledger` carry a product **reference** (`product_external_id`) + immutable **snapshot** (`product_name`/`product_sku`), and `qr_batches` carries its own `manufacturer_id`. The catalog lives in **`product_points`**, where `source = 'import'` marks a real product (`name`, `sku`, `points`, plus **`attrs`** — a JSON object holding every *other* CSV column keyed by its original header text, so the panel renders whatever the manufacturer's file contained). Rows with `source IS NULL` are legacy points-overrides for Vastra designs and are **not** part of the catalog.

`GET /catalog/products` returns `{products, columns, source}` and resolves in strict precedence, **never merged**: imported rows → else the hardcoded `_SAMPLE_PRODUCTS` when `USE_SAMPLE_PRODUCTS` (**default off**; set `1` for local dev/demos) → else `[]` and the panel prompts for an import. `POST /catalog/products/import` takes `{csv, mode}` where mode is `upsert` (match on product code, refresh name/attrs, add new, delete nothing, **keep panel-set points unless the CSV has a points column**) or `replace` (drop this manufacturer's imported rows first, leaving legacy rows alone). Required CSV columns are a **product name** and a **product code** (matched case/format-insensitively via `_pick_col`/`_norm_header` against `_CSV_NAME_HEADERS`/`_CSV_CODE_HEADERS` — see the CSV-import section above); a points column is optional and matches `retailer_points` as well as `points`; row-number columns (`SNo`) are dropped and literal `null`/`N/A`/`-` cells normalize to empty. The product code alone is the identity → `product_external_id`. `DELETE /catalog/products/{external_id}` removes one imported product and `DELETE /catalog/products` clears the whole imported catalog (the panel's **Delete all**, behind a confirm; returns `{deleted: n}` and spares legacy rows); `PUT /catalog/products/{external_id}/points` edits points (on a *sample* it writes a `source IS NULL` override, so editing a sample never flips the account into an imported catalog). Deleting or replacing never affects issued QR codes — that is what the snapshots are for. `POST /qr/generate` still takes `product_external_id` + `product_name` + `product_sku` + `points_per_code` directly, with **no** catalog lookup. `_backfill_product_snapshots()` (startup, idempotent) fills the snapshot columns for pre-migration rows.

**Vastra's product API is not a catalog source.** `get-design-ids` returns design numbers but no design *name*, so it could only ever supply unusable product names. `fetch_vastra_products()` stays in `app/vastra_client.py` **dormant and uncalled** for a future reconnect; there is deliberately no `USE_VASTRA_API` flag. Vastra **OTP login is a separate path, always on**, and still stores `vastra_access_token` (which that reconnect would need). **Legacy, kept only for backward reads:** the `products` table and `GET /products` remain (still read by the Schemes and Claims panel tabs and `/web/generate`, and by `qr_batches.product_id`/`scheme_products.product_id` on historical rows) — but product CRUD (`POST`/`PATCH`/`DELETE /products`) and `POST /products/import` are **removed**; no new rows are written to `products` going forward. `scheme_products` is still keyed by the legacy local `product_id`, so product-specific scheme bonuses currently only work for old local products — imported products can't be scheme-scoped until that table migrates to `product_external_id` (not done yet). When editing QR/scan/claims/analytics SQL, read the snapshot columns — do not re-introduce a `products` join. See `docs/integration/PRODUCT_INTEGRATION.md`.

**Parent/child QR (boxes).** `qr_codes` rows are children by default; if `items_per_box` is set at generation, parent (box) codes are created with children pointing at them via `parent_token`. Scanning a parent registers all still-unredeemed children at once and sums their points. A box scan therefore writes **one `points_ledger` row per child**; `GET /claims` re-collapses them for display by grouping on `COALESCE(q.parent_token, l.token)` (join `qr_codes`), returning `item_count` + `parent_token` so the panel shows a single `📦 Box · N items` row. This grouping is **query-time only** (no `scan_event_id` column) — keep it that way so it stays correct for data already in production. The box (parent) sticker in `app/pdf_service.py` keeps its title/name/code inside the border, so its QR is sized smaller than a child sticker's.

**QR payload.** Each code encodes `{QR_BASE_URL}/{token}` (default `/web/scan`); set `QR_BASE_URL` to the deployed HTTPS origin before any production print run, or printed codes point at the wrong host. The 6-char `manual_code` is the typed fallback for damaged stickers. The token is a `uuid4().hex` lookup key — opaque, unguessable, and validated server-side (unknown → 404), so tampering with the URL can't corrupt anything; `scan.html` cosmetically rewrites the address bar to `/web/scan` after reading it.

**Retailer location & the map.** Two layers, distinct on purpose: (1) the **retailer's shop pin + address** — `retailers.lat/lng`, `location_source` (`city` = resolved from the typed region via `geo.coords_for`; `gps` = captured from a scan), and `retailers.address` (a precise street address). These are **refreshed every scanning session — latest wins** (via `POST /retailer/location`): the pin moves, `region` is re-derived from `geo.nearest_city`, and the address is reverse-geocoded best-effort by `geo.reverse_address` (free OpenStreetMap Nominatim; falls back to the previous value / the city / the coordinates). So a wrong city entered at registration self-corrects to the real one. `region` is **optional** at registration. The Customers tab shows the address + a Google Maps **"View on map"** link to the exact pin. (2) **Per-scan location** — `points_ledger.lat/lng`, sent with `POST /scan`. The dashboard `map_points` plots scan *events* (bucketed ~11m, weighted by count), **clustered** via `leaflet.markercluster` with street-level zoom, falling back to the shop pin for scans with no location. **Location is asked up front**, before scanning, via a trust-framed popup in `scan.html` (high-accuracy GPS, secure-context required); if the retailer can't/won't grant it they close the popup (✕) and the scan falls back to their **registered city** — scanning is never hard-blocked.

**Panel ↔ API.** `panel/src/api.js` is the only fetch layer: dev hits the Vite proxy (`/api` → `:8000`), production is same-origin (`/panel` served by the API). Manufacturer session token lives in `localStorage` (`vl_token`); retailer webviews use `vl_rtoken`. Navigation is a single top-right **burger menu** (`App.jsx`) listing the tabs + Log out. Every points-changing action (adjust/transfer/approve/reject; gift claim in the webview) is gated by a themed confirmation dialog — in the panel via the promise-based `useConfirm()` (`panel/src/confirm.jsx`, mounted by `ConfirmProvider` in `main.jsx`). The panel renders manufacturer tabs (Dashboard, Customers, Distributors, Products, Schemes, Gifts, Claims, Redemptions) or, for super admin, the Manufacturers tab. Every data tab has an **Export CSV** button backed by a shared client-side helper `panel/src/utils/csv.js` (`downloadCSV(filename, columns, rows)` — RFC-4180 + BOM `Blob`, no dependency, no new endpoint); Claims walks all pages and Redemptions exports all three statuses. The four imported lists (Products, Customers, Distributors, Gifts) each pair their **Import CSV** button with a **Delete all** gated by `useConfirm()`; Customers and Gifts surface the `{deleted, skipped}` result as a notice explaining which rows survived and why. The **Products** tab has a client-side **search** (product name or code only — the free-form CSV columns are deliberately not searched, so a match is always visible on screen) and is client-paginated (rows-per-page 10/25/50/100, default 10 — the catalog is returned whole, so Export CSV covers every *matching* row, not just the visible page). Its table pins Product name + code to the left and Points + Actions to the right (`.catalog-table` in `styles.css`), leaving only the manufacturer's own CSV columns to scroll horizontally. Those sticky offsets depend on widths set on an inner `.cell` wrapper — a `th`/`td` width is only a hint under `table-layout: auto` — so if you change a sticky column's width, update the matching `left`/`right` offset (neighbouring `.cell` width + 20px of cell padding). **Generate QR** on the Products tab opens an in-panel modal `panel/src/components/GenerateQrModal.jsx` (it calls the existing `/qr/*` endpoints via `api.js` + `printUrl`), so the standalone `/web/generate` page is no longer linked from the panel (it still works on its own). The retailer webviews (`home/scan/shop/claims`) share their own top-right burger menu (Home/Scan/Reward shop/Claims history/Log out), and `scan.html` plays a count-up + confetti animation on a successful scan (and reopens the camera on "Scan another").

**Theming.** The Vastra brand palette is a set of CSS variables in `panel/src/styles.css` `:root` (`--primary` `#0191d0`, `--indigo` `#1d466f` dark blue, `--madder` `#fb624b` coral, `--ink` `#112134`, light `--paper`/`--card`; `--leaf`/`--gold` kept as functional approved/pending status colors). The **same `:root` block is duplicated inline in every `app/web/*.html`** — change all of them together, plus the non-variable literals that derive from the palette (chart colors in `Dashboard.jsx`/`BarChart.jsx`, the `scan.html` confetti array, Leaflet `.scan-dot`/`.marker-cluster` colors, `.error`/badge tints, modal `.backdrop`/`.modal-backdrop` overlays). Font is a **Helvetica system stack** (no web-font link); headings are bold, codes/tokens use a monospace stack. **QR codes stay black/white** (`app/qr_service.py`) for scanner reliability — don't tint them.

**Dashboard analytics (`GET /analytics/dashboard`, manufacturer-scoped).** Returns `totals` (retailers, products, scans, points_awarded, codes_issued, **redeem_total/redeem_pending/redeem_approved** from `gift_claims`), `by_region`/`by_product`/`by_distributor`/`top_retailers`, `map_points` (clustered Leaflet India scan map via `leaflet.markercluster`), and **`by_month`** (`{month:'YYYY-MM', generated, scanned}` — generation from `qr_codes.created_at`, scans from `points_ledger.scanned_at`). The Dashboard shows two stat rows (funnel totals + redemption requests), the region/distributor tables, and a **QR analytics** section with a year selector + two themed SVG bar charts (`panel/src/components/BarChart.jsx`, no charting dependency). Month buckets use `substr(x, 1, 7)` — **not** `strftime` — to stay portable across SQLite and MySQL. Blank/NULL regions roll up under `'Unspecified'` (`COALESCE(NULLIF(region, ''), 'Unspecified')`). Cards are all-time; the charts are per-month within the selected year (each chart shows a per-year subtotal so the bars reconcile).

## Deployment

**Env vars must be set in the host's own settings — `.env` never deploys.** The app has **no dotenv loader**: locally you pass `--env-file .env` to uvicorn (and `.env` is gitignored, so it is not in any image). On Render every variable has to exist in the service's Environment tab or the feature fails closed there while working perfectly in local dev — the usual symptom is `502 "VASTRA_API_BASE_URL is not configured"` on the panel's Vastra OTP login. Non-uvicorn entry points (`seed.py`, `import_retailers.py`, pytest) don't read `--env-file` either; export into the shell instead (`set -a; source .env; set +a`).

`Dockerfile` builds the panel then runs the API serving everything (`/`, `/panel`, `/web/*`). Render + MySQL: set `DATABASE_URL` (`mysql://user:pass@host:3306/db?ssl=true` — a leftover `postgres://` URL is rejected at boot) and `QR_BASE_URL=https://HOST/web/scan`; set `SSO_SECRET` to enable native-app SSO (unset → SSO endpoints inert); set `VASTRA_API_BASE_URL` (+ optional `VASTRA_API_KEY`/`VASTRA_API_TIMEOUT`/`VASTRA_UDID`/`VASTRA_DEVICE_TYPE`) to enable **Vastra OTP login** (unset → it fails closed with `502`; password login still works); `USE_SAMPLE_PRODUCTS` defaults to off, so the Products tab shows the import prompt rather than the three built-in demo products unless you explicitly set `1`. The container creates/migrates tables on boot but never seeds — data persists across deploys. The `external_id` columns and their unique indexes are added idempotently by `migrate()`/`create_constraints()` like any other additive change. See `DEPLOY.md` and `docs/integration/MYSQL_SETUP.md`.
